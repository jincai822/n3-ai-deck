## 1. 执行摘要

N3 AI Deck 要为在 Linux 上频繁使用 AI、软件和自动化流程的个人创作者与开发者，提供一个本地优先的实体生产力控制台：用户通过妙联宝/Mirabox N3 V3.0 的 LCD 按键、圆形按键和旋钮触发工作流，并在设备或本地界面看到明确结果。产品从当前“公开仓库已建立、目标硬件只能被系统识别”的状态，逐步交付安全发现、硬件控制、可扩展动作引擎和一个真实 AI 工作流演示。首个可验证产品结果是：在不泄露凭据、不误写硬件的前提下，完成 10/10 次预定义端到端黄金流程。

🔶 **假设：** 产品负责人提出的提高自动化程度、减少人工协调时间的诉求，也代表一类可服务的 AI 重度用户；目前没有外部用户访谈证明该细分市场的规模或付费意愿。

## 2. 问题陈述

### 2.1 谁遇到这个问题

- 已确认的首位用户是产品负责人本人：拥有 N3 V3.0 硬件、项目需求、上游源代码和自动化开发方案，希望尽量减少重复协调和手工执行。
- 🔶 **假设：** 相同问题也存在于 Linux 上频繁切换 AI 助手、终端、编辑器和桌面工具的开发者、创作者与小团队操作者。

### 2.2 可观察的问题

1. AI、应用和脚本分散在不同窗口，常用流程需要多次点击、复制、粘贴和确认，难以形成稳定的肌肉记忆。
2. 当前仓库沿用上游面向 `6603:1003` 的实现，而实机枚举为 `6602:1000`；直接把新 USB ID 接入活跃 SDK 可能触发打开设备或后续写操作，风险不可接受。
3. 公开仓库目前只能说明愿景和路线图，尚无可重复的实机产品演示，潜在客户或合作方无法判断产品效果。
4. 大项目上下文、需求、任务拆分、代码实现和验证若主要依靠聊天中人工搬运，会消耗产品负责人的时间。🔶 **假设：** 结构化自动任务队列能减少遗漏；目前只有 M0 的一次交付记录，没有长期对照数据。

### 2.3 影响

- **用户影响：** 重复操作占用注意力；自动化难以发现、配置和复用；硬件兼容试错可能影响设备。
- **产品影响：** 缺少真实效果、截图/视频和可验证路线图。🔶 **假设：** 补齐这些证据会提高对外展示和合作沟通的可信度；尚无合作方反馈数据。
- **交付影响：** 如果没有 PRD、可执行故事、自动测试和人工安全门，AI Coding 可能快速地产生错误范围内的代码。

### 2.4 证据

| 证据 | 结论 | 强度 |
|---|---|---|
| 产品负责人在需求澄清中明确要求提高自动化程度、减少人工耗时 | 自动化开发与自动化使用都是核心诉求 | 单一首发用户的直接证据 |
| Linux 只读观测到目标设备 `6602:1000`、设备版本 `0300` 和两个 HID 接口 | 目标硬件与上游主要示例 `6603:1003` 不同 | 实机技术证据；未记录序列号 |
| M0 已建立公开仓库、双语说明、CI 和安全边界 | 可以在稳定公开基础上增量开发 | 仓库证据 |
| 现有 daemon、debug、probe 和 GUI 多处硬编码 `6603:1003`，部分路径会打开或写入设备 | 兼容工作必须先隔离只读发现和活跃设备访问 | 代码证据 |

🔵 **开放问题：** 尚无外部客户访谈、使用分析、竞品研究或付费数据；在获得这些证据前，本 PRD 不主张市场规模或收入目标。

## 3. 目标用户与角色

### 3.1 首要角色：自动化型 AI 操作者

- **角色：** 独立开发者、创作者或技术型产品负责人。
- **环境：** Linux 桌面；同时使用 AI 对话、IDE、终端、浏览器和本地脚本；愿意做初始配置，但不希望持续维护脆弱自动化。
- **目标：** 一次实体操作启动常用工作流；快速看懂执行状态；把重复开发步骤交给 AI Coding 自动完成。
- **痛点：** 工具切换多、上下文分散、流程反馈不一致、硬件兼容风险高。
- **当前行为：** 通过聊天澄清需求，再人工传递项目上下文和逐步确认执行。

🔶 **假设：** 首要角色愿意为一次性本地配置投入最多 30 分钟，并偏好本地凭据与可审计动作；需要在 M4 前通过至少 5 次目标用户访谈验证。

### 3.2 次要角色：合作方与插件开发者

- **角色：** 希望评估集成机会的潜在客户、合作伙伴或开源贡献者。
- **目标：** 在数分钟内理解产品效果、兼容范围、扩展边界和路线图，并能在没有实机与商业私有代码时运行测试。
- **差异：** 更关注可信演示、API 稳定性、许可证和集成成本，而不是首位用户的个人工作流。

🔶 **假设：** 稳定的公开插件协议和一个真实演示足以促成早期合作对话；目前没有合作漏斗数据。

### 3.3 Jobs-to-be-Done

- **功能任务：** 当我要重复执行一个 AI 或桌面流程时，我希望用一个可记忆的实体动作启动它并看到结果，从而减少窗口切换和重复输入。
- **情绪任务：** 我希望确信自动化行为可预测、可停止、不会泄露凭据或误操作硬件。
- **社会任务：** 我希望向客户或合作方展示一个真实、专业、可扩展的产品，而不是只有概念或脚本集合。

🔶 **假设：** 上述情绪和社会任务来自当前项目目标推断，仍需外部访谈验证。

## 4. 战略背景

### 4.1 业务目标

- 建立一个客户与合作方可直接理解的公开产品入口。
- 采用 Open Core：公开设备集成、本地动作、插件协议、诊断、UI、文档和测试；保留托管同步、企业管理、付费连接器及客户专属部署为商业扩展。
- 用真实硬件证据和可重复演示建立技术可信度，再决定商业化优先级。
- 用 PRD → 小故事 → AI 实现 → 独立审核 → CI 的流水线，减少产品负责人日常协调成本。

🔵 **开放问题：** 尚未定义收入模型、价格、获客渠道和商业指标；这些问题不阻塞 M1–M3 的技术验证，但必须在 M4 对外获客前决定。

### 4.2 当前替代方案与差异

- 当前替代方案包括键盘快捷键、宏工具、桌面启动器、通用 Stream Deck 软件和自建脚本。
- N3 AI Deck 的目标差异是：Linux、本地优先、面向 AI 工作流、明确的设备反馈、开放插件边界以及可审计的安全默认值。

🔶 **假设：** 这些差异对目标用户有足够价值；未进行系统竞品研究，不能据此声称“唯一”或“领先”。

### 4.3 为什么是现在

- 目标硬件已经接入并得到只读 USB/HID 证据，可以从真实设备约束出发。
- M0 公开基础已经完成且 CI 通过，可以增量交付而不是重做仓库。
- 产品负责人已经批准产品方向、Open Core 边界和 AI 生产力控制台定位。

## 5. 方案概述

### 5.1 产品体验

用户在本地配置“实体控件 → 动作/工作流”的映射。设备事件经过安全设备适配层转为标准事件，再由动作引擎调用本地自动化或 AI 插件。执行结果采用结构化状态返回本地 UI，并在完成硬件写入验证后可选显示到 LCD 按键。没有 AI 凭据时，本地自动化仍可使用。

```text
N3 控件
  -> 安全设备适配层
  -> 标准事件
  -> 动作引擎
  -> 本地或 AI 插件
  -> 结构化结果
  -> UI / 日志 / 可选 LCD 反馈
```

### 5.2 分阶段交付

| 里程碑 | 用户结果 | 硬件安全门 |
|---|---|---|
| M1 安全发现 | 系统可以明确说明是否发现与 `6602:1000` 匹配的候选设备及其接口拓扑 | 只读 `/sys`；不打开 `/dev`；不调用 SDK |
| M2 硬件控制 | 用户的按键、圆键、旋钮、亮度和六块 LCD 经过分阶段真机验证 | 每个写入阶段都需产品负责人明确批准 |
| M3 动作引擎 | 用户可以把标准设备事件映射到安全的本地插件 | 默认不执行任意下载内容或未配置命令 |
| M4 AI 演示 | 用户可运行一个真实 AI 工作流并看到清晰状态 | 凭据只在本地提供且不进入日志/设备图片 |
| M5 `v0.1.0` | 客户或合作方可复现安装、演示与测试 | CI 和完整物理清单通过后才发布 |

### 5.3 自动化交付系统

- 正式 PRD 是范围与验收标准的唯一产品基线。
- 每个里程碑拆为可独立验证的小故事；每次只实现一个故事。
- AI Coding 自动完成代码、测试、静态检查、独立复核和进度记录。
- 只有硬件写入、系统级安装、秘密提供、发布标签等高风险动作保留人工门。
- 任何第三方自动化模板在许可证和安全默认值核验前不复制到公开仓库；本项目只实现已审查、可审计的自动化流程。

### 5.4 Open Core 边界

- **公开核心：** 设备发现与通信、本地动作引擎、插件协议、基础插件、本地配置与诊断、测试和文档。
- **商业扩展：** 云同步、企业身份与策略、付费连接器、客户专属工作流、托管部署、计费与商业分析。
- 公开核心不得导入或依赖私有包。

### 6.3 护栏指标

- 未经明确人工批准的硬件初始化、亮度或 LCD 写入：**0 次**。
- 诊断、夹具、日志和公开提交中的 API 密钥与设备序列号：**0 个**。
- 未通过发布门却宣称兼容或生产就绪：**0 次**。
- 公开核心对私有商业包的运行时依赖：**0 个**。

🔵 **开放问题：** 节省时间、周活跃使用、留存和付费转化的基线不存在；M4 真实试用前不设虚假目标。

## 7. 用户故事与需求

### 7.1 Epic 假设

我们相信，为自动化型 AI 操作者提供一个安全、本地优先、可见反馈的实体控制台，可以把分散的重复操作变成可靠的一步工作流。我们首先通过 M1–M4 的技术门和 10/10 黄金流程验证可行性，再通过外部访谈验证是否真正节省时间并产生合作或付费价值。

### US-01：安全识别目标设备（M1）

作为设备所有者，我希望先只读发现与 `6602:1000` 匹配的候选设备和接口拓扑，从而在任何初始化或写入前取得供人工确认的证据。

**验收标准：**

- [ ] 能匹配 `6602:1000`，并同时显示“机主报告的型号候选、身份未确认、协议未验证”。
- [ ] 发现路径只读取 `/sys` 元数据，不打开 `/dev/hidraw`、input event 或 vendored SDK。
- [ ] 输出不包含序列号，且在无设备、权限/数据缺失和重复设备时行为确定。
- [ ] 假设备夹具和实机只读记录都通过专项 PRD 的门槛。

### US-02：验证全部实体控件（M2）

作为设备所有者，我希望分阶段验证每类输入和显示能力，从而建立可追溯的兼容证据。

**验收标准：**

- [ ] 先完成只读输入，再依次验证初始化、亮度、单图和六图显示。
- [ ] 每个阶段记录提交、预期、实际结果和恢复方式；失败会阻塞后续写入阶段。
- [ ] 只有证据覆盖的能力才更新兼容表。

### US-03：配置实体控件动作（M3）

作为 AI 操作者，我希望把按键或旋钮映射到本地动作，从而复用常见工作流而不修改核心代码。

**验收标准：**

- [ ] 标准事件不暴露具体供应商协议细节。
- [ ] 插件声明元数据、配置校验、执行和结构化结果。
- [ ] 插件失败、超时或缺少配置不会使设备服务崩溃。
- [ ] 默认配置不执行任意 shell、下载内容或未信任脚本。

### US-04：运行 AI 工作流（M4）

作为 AI 操作者，我希望一次实体操作运行一个真实 AI 流程并看到状态，从而减少重复交互时间。

**验收标准：**

- [ ] 至少一个端到端场景从设备事件运行到结构化结果。
- [ ] 运行中、成功、失败和超时状态可区分。
- [ ] 凭据由用户在本地提供，绝不进入仓库、诊断或 LCD 图像。
- [ ] 黄金场景连续 10 次运行成功并留存非敏感证据。

### US-05：评估和扩展公开项目（M3–M5）

作为合作方或插件开发者，我希望快速理解产品效果和扩展契约，从而判断是否集成或合作。

**验收标准：**

- [ ] 无实机即可运行公开核心测试和示例插件。
- [ ] README 明确区分已实现、验证中和计划能力。
- [ ] 真实演示媒体、兼容表、路线图和插件文档相互一致。
- [ ] 许可证、上游署名和商业边界明确。

## 8. 不在首个公开版本范围内

- Windows 和 macOS 支持：先证明 Linux + 实机主路径。
- 支持所有 Stream Dock 型号：未知 ID 必须安全拒绝。
- 云同步、远程管理、企业账号、计费和商业分析：属于商业扩展或后续验证。
- 插件市场：先验证插件协议和一个真实场景。
- 自主执行高风险动作：硬件写入、系统安装、秘密处理和正式发布保留人工门。
- 将现有上游 GUI 全面重写：优先建立安全边界和可验证纵向切片。
- 对市场份额、生产就绪或完整兼容作无证据承诺。

## 9. 依赖与风险

### 9.1 依赖

- **技术：** Linux sysfs/HID、现有 Python 包和 vendored SDK、GitHub CI、机主报告为 N3 V3.0 的候选实机。
- **外部：** 上游项目与 Mirabox SDK 的协议知识和许可证条款。
- **人工门：** 产品负责人批准硬件写入、系统级安装、真实 AI 凭据和正式发布。

### 9.2 风险与缓解

| 风险类型 | 风险 | 缓解措施 | 责任人/触发点 |
|---|---|---|---|
| 价值 | 目标用户不认为实体控制台比快捷键更省时间 | M4 前访谈并测量真实任务时间；无改善则收缩场景 | 产品负责人，M4 前 |
| 易用性 | 初始配置成本抵消日常收益 | 先做一个默认黄金流程，测量首次可用时间 | 产品负责人，M4 验收 |
| 可行性 | `6602:1000` 与上游 N3 协议不完全兼容 | M1 被动发现；M2 分阶段实验；未知能力默认关闭 | 技术负责人，每个硬件门 |
| 安全 | 注册 VID/PID 后现有 SDK 自动打开或写入设备 | M1 使用独立被动目录，不修改活跃 SDK 注册表 | 技术负责人，M1 |
| 隐私 | 日志或夹具泄露密钥、序列号、用户名或本机路径 | 结构化脱敏输出、公开扫描测试、无序列号策略 | 每个 PR |
| 交付 | AI Coding 越权、循环或生成未经验证代码 | 沙箱、单故事预算、测试优先、独立审阅和 CI | 每个故事 |
| 许可 | vendored SDK 条款不支持计划中的商业二进制分发 | 在首个商业二进制前完成法律/许可证核验 | 产品负责人，M5 前 |
| 维护 | 上游更新与本项目边界长期分叉 | 保留 upstream remote、集中适配层、记录来源 | 技术负责人，升级时 |

## PRD 自评

### 最强部分

第 5、7、9 节：阶段性架构、安全门和验收范围有仓库代码与实机只读证据支持，能够直接指导工程拆分。

### 最弱部分

第 3、4、6 节的外部市场与价值指标：目前只有产品负责人这一位已确认用户，没有外部访谈、行为数据或商业基线。

### 优先验证的假设

| # | 假设 | 错误时的影响 | 验证方式 |
|---:|---|---|---|
| 1 | Linux AI 重度用户愿意使用实体控制台 | 产品定位过窄或无需求 | M4 前完成至少 5 次目标访谈 |
| 2 | 一步实体工作流能显著节省时间 | 首要价值不成立 | 对同一任务进行人工/控制台计时对比 |
| 3 | `6602:1000` 可沿用或小幅适配 N3 协议 | M2 成本和硬件风险上升 | 严格按只读输入到可逆写入分阶段验证 |
| 4 | 开放插件核心能带来合作机会 | Open Core 商业路径不成立 | 发布演示后跟踪真实咨询和集成意向 |

### 建议下一步

执行已批准的 M1：先交付独立、纯 stdlib、只读 sysfs 发现能力；通过自动测试和实机只读记录后，再决定 M2 的 SDK 激活与权限方案。
