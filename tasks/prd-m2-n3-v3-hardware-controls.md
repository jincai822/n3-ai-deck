## 1. 执行摘要

M2 为机主报告的妙联宝 N3 V3.0 候选设备 `6602:1000` 建立一个默认关闭、逐能力
晋级的安全硬件适配层。主进程使用窄接口 `N3Adapter` 和能力状态机；所有真实设备
访问都在短生命周期辅助进程中执行，默认开发与 CI 只使用 `FakeBackend`。

M2 先验证精确设备档案和接口职责，再按“只读输入 → 可声明初始化 → 亮度 → 单 LCD
→ 六 LCD”的顺序推进。每个阶段都有独立人工批准、固定命令清单、超时、人工观察和
恢复合同。任何失败阻塞后续能力；断连后不自动重连或恢复写入。

M2 不直接把目标加入 vendored SDK 全局产品表，不复用会自动 heartbeat、组合初始化、
写图或执行 shell action 的 legacy daemon/probe/debug/GUI，也不安装现有 vendor-wide
`0666` udev 规则。

## 2. 问题陈述

### 2.1 用户问题

设备所有者希望把 N3 V3.0 变成 AI 生产力控制台，但当前只有被动发现证据，尚不知道
两个 HID 接口各自承担什么职责，也没有 `6602:1000` 的事件、亮度和显示协议验证。
直接复制上游 `6603:1003` 路径会让闭源 native SDK 在不透明的生命周期中自动发送
heartbeat、组合初始化和 disconnect，并可能触发已知清理崩溃。

用户需要一种既能最大化 AI Coding 自动化、又不会把未经验证的代码直接接到硬件上的
开发方法。关键问题不是“能否尽快让屏幕亮起来”，而是“如何建立以后可以安全复用、
可测试、可审计、失败可停止的硬件边界”。

### 2.2 当前证据

M1 已确认：

- 目标 USB ID 是 `6602:1000`，`bcdDevice=0300`。
- 接口 `00` 是 HID `03/00/00`。
- 接口 `01` 是 HID Boot Keyboard `03/01/01`。
- 两个接口均为候选，`interface_selection=ambiguous`。
- 身份仍是 `user_reported_candidate`，协议仍是 `unvalidated`。

代码审查确认：

- 活跃 SDK 表没有精确 `6602:1000`。
- 旧 `open()` 自动启动 reader 和 heartbeat；旧 `close()` 发送 disconnect。
- 旧 `init()` 同时 wake、设亮度 100、清屏、读取固件并 refresh。
- legacy daemon/probe 会初始化、调亮度和写图；dry-run 不代表硬件只读。
- 旧 udev 规则只匹配 vendor `6603` 并授予 USB/hidraw/input `0666`。
- native transport 只有二进制，线程、超时、返回码和清理行为不能被完整审计。

## 3. 目标用户与 Jobs-to-be-Done

### 3.1 首要用户

首要用户是拥有当前候选设备、希望用 AI Coding 快速开发 N3 AI Deck，同时要求所有
物理风险步骤可见、可批准、可停止的产品负责人。

🔶 **假设：** 首批外部贡献者也需要相同的 FakeBackend 和分阶段验证方法，但 M2 不以
外部用户采用率作为完成门。

### 3.2 Jobs-to-be-Done

- 当 AI Coding 开发设备层时，我希望绝大部分代码和测试不依赖真机，从而持续自动推进。
- 当需要首次访问硬件时，我希望看到唯一接口、唯一动作、预期、时限和恢复方式，从而只
  批准我理解的风险。
- 当 native SDK 崩溃或设备断开时，我希望主程序仍然存活且后续写入停止，从而不形成
  自动重试或反复初始化。
- 当项目对外展示兼容性时，我希望每项能力都由实机证据支持，从而不向客户或合作方夸大。

## 4. 战略背景

M2 是“发现设备”到“控制设备”的边界里程碑。它为 M3 的动作与插件系统提供真实的
标准化输入和显示能力，但不把动作执行、AI 凭据或产品 GUI 混入协议验证。

采用独立 Adapter 而不是修改 vendored SDK，可以让公开基础层拥有稳定合同，也为未来
替换闭源 transport、支持其他 backend 或把商业扩展放在公共接口之外保留空间。辅助进程
隔离使本项目能够在保留上游参考价值的同时，不把 native 稳定性当作主进程可靠性的前提。

## 5. 目标、非目标与成功结果

### 5.1 目标

- 建立精确、不可由 USB ID 自动激活的 `6602:1000` active profile。
- 建立窄接口 `N3Adapter`、能力门、版本化 IPC 和隔离 helper 生命周期。
- 提供 FakeBackend，使 G0 代码与测试不需要 SDK、硬件、root 或 `/dev`。
- 分别验证 6 个 LCD 键、3 个圆键、3 个旋钮、亮度、单屏和六屏。
- 对权限、SDK 加载和每种写入建立独立人工批准门。
- 对超时、崩溃、断连、部分写入和恢复失败定义稳定行为。
- 发布逐能力兼容状态和脱敏证据。

### 5.2 非目标

- 插件协议、动作引擎、AI 工作流、凭据管理或任意 shell action。
- legacy daemon/GUI/systemd 对目标设备的自动接管。
- 自动安装 udev、sudo 提权、修改系统 ACL 或启动服务。
- 自动重连后刷新 LCD 或恢复亮度。
- GUI 重写、跨平台支持、云同步、账户、市场或商业扩展。
- 由一次成功推导所有 `6602:1000` 或所有 N3 V3.0 硬件兼容。

### 5.3 用户可见成功结果

M2 完成时，仓库能够诚实展示：哪些实体输入已经验证、亮度是否受控、六块 LCD 是否
映射正确、使用了什么固件/接口证据，以及哪些能力仍未验证。开发者可以在没有设备的
环境中运行完整 Adapter 合同测试。

## 6. 方案概述

### 6.1 已批准架构

```text
M1 passive discovery
        -> DeviceProfile
        -> CapabilityGate
        -> N3Adapter
             -> FakeBackend
             -> ReadOnlyInputHelper
             -> VendorSdkHelper
        -> RedactedEvidenceRecorder
```

主进程禁止直接导入 `_vendor` 或加载 native transport。`FakeBackend` 是默认后端。
`ReadOnlyInputHelper` 不导入 SDK 且只能以只读模式访问已批准接口。未来主动操作由
`VendorSdkHelper` 在单阶段、短生命周期进程中执行。

### 6.2 能力状态机

```text
CANDIDATE
  -> PROFILE_APPROVED
  -> INPUT_VALIDATED
  -> INITIALIZATION_VALIDATED
  -> BRIGHTNESS_VALIDATED
  -> ONE_LCD_VALIDATED
  -> SIX_LCD_VALIDATED
```

- 前置状态未满足时禁止越级。
- 阶段失败进入 `BLOCKED`。
- 断连进入 `DISCONNECTED`，输出状态为 `unknown`。
- 重插后从 M1 被动发现开始新 session。
- 不自动恢复曾经批准的能力或写入。

### 6.3 阶段清单

每次未来真机执行都必须使用不可变阶段清单，包含：

- schema 版本、stage、软件 commit、profile digest 和精确接口。
- 允许操作、最大调用次数、参数范围和 deadline。
- 预期机器结果和人工观察项。
- 停止条件、恢复计划和批准引用。

helper 拒绝清单外的命令。IPC 不提供通用 raw write、任意 method name 或 native symbol。

## 7. 功能需求与用户故事

### M2-00：建立零硬件开发基线

作为维护者，我希望用 FakeBackend 实现和验证完整 Adapter 合同，从而让 AI Coding 在
不接触真实设备时自动推进。

**验收标准：**

- [ ] 默认运行、测试和导入不会加载 `_vendor` 或 native `.so`。
- [ ] 默认运行不打开 `/dev`、不读取默认 input/hidraw、不调用 sudo 或系统服务。
- [ ] FakeBackend 能产生全部按钮、旋钮、超时、错误和断连场景。
- [ ] CI 验证状态机、IPC、恢复队列、隐私和失败关闭。
- [ ] 现有测试继续通过，新增测试不要求真机。

### M2-01：建立精确 active profile

作为设备所有者，我希望 active profile 精确绑定身份和接口证据，从而避免 USB ID 命中
自动变成硬件支持。

**验收标准：**

- [ ] profile 要求 VID `6602`、PID `1000`，并保存允许的 `bcdDevice` 证据。
- [ ] profile 只保存脱敏、稳定字段，不保存 serial、总线位置或 `/dev` 编号。
- [ ] M1 observation 不自动创建或批准 active profile。
- [ ] 身份、固件或接口不一致时失败关闭。
- [ ] 接口仍 ambiguous 时，不允许进入真实 input helper。
- [ ] 不修改 `ProductIDs.g_products`，legacy DeviceManager 不会发现目标。

### M2-02：隔离 Adapter 与 helper

作为维护者，我希望主进程只通过版本化 IPC 调用受限 helper，从而隔离 native 崩溃和
阻塞。

**验收标准：**

- [ ] 主进程不直接导入 vendored SDK。
- [ ] Adapter 只暴露类型化输入、初始化、亮度、单键图片和关闭会话操作。
- [ ] IPC 验证 schema、commit、profile digest、接口、允许操作和 deadline。
- [ ] helper crash、timeout、异常退出和不完整响应不会终止主进程。
- [ ] 每个 helper 只运行一个批准阶段；无后台常驻和无自动重启。
- [ ] 生产 API 不提供 raw write、任意函数调用或 shell action。

### M2-03：验证实体输入

作为设备所有者，我希望先观察所有实体输入且不写设备，从而确认接口与事件映射。

**验收标准：**

- [ ] helper 只以只读方式打开唯一已批准接口，不导入 SDK。
- [ ] helper 不发送 heartbeat、feature/output report、init、refresh 或 disconnect write。
- [ ] 无法证明无写入时，阶段阻塞，不回退到 legacy `open()`。
- [ ] LCD 键 1–6 各完成 10/10 press/release。
- [ ] 圆键 7–9 各完成 10/10 press/release。
- [ ] 三个旋钮各完成左右 20/20、按压/释放 10/10，方向无误。
- [ ] 10 分钟会话无崩溃、未授权写入或未知事件；事件延迟目标 p95 ≤250ms。
- [ ] 拔线后 2 秒内进入断连状态，重插后不自动打开或写入。

### M2-04：执行可声明初始化

作为设备所有者，我希望初始化只执行已批准的生命周期命令，从而避免组合 `init()` 的
未知副作用。

**验收标准：**

- [ ] 永久禁止调用 legacy 高层组合 `StreamDock.init()`。
- [ ] 操作前列出所有 wake、握手、refresh、heartbeat、disconnect 或其他实际写入。
- [ ] 只能绑定精确 profile 和接口；不使用全局枚举或 `devices[0]`。
- [ ] 每种命令都有调用次数、返回分类、deadline 和恢复说明。
- [ ] 实际写集合无法证明时不执行。
- [ ] 初始化后重新运行输入验证，不得出现映射回归。

### M2-05：验证可逆亮度

作为设备所有者，我希望在已知基线下做一次受限亮度变化并恢复，从而确认亮度能力而不
影响 LCD 内容。

**验收标准：**

- [ ] 操作前由机主确认已知基线 `B`；未知时阶段阻塞。
- [ ] 清单只允许 `B-10` 和恢复 `B` 两次亮度写入。
- [ ] SDK/transport 结果、人工可见变化和恢复三者均成功。
- [ ] LCD 图片和输入映射不改变。
- [ ] 超时、无变化、副作用或恢复失败都会阻塞图片阶段。

### M2-06：验证单块 LCD

作为设备所有者，我希望先只写一块可识别测试图，从而限制未知图片协议的影响面。

**验收标准：**

- [ ] 只允许 LCD 1 和一张唯一高对比测试图。
- [ ] 操作前确认可恢复基线；未知原图只能使用机主批准的替代基线并如实记录。
- [ ] 只有 LCD 1 改变，位置、方向和裁切正确，无相邻屏串扰。
- [ ] 恢复批准基线并稳定 60 秒。
- [ ] 任一失败阻塞六屏验证。

### M2-07：验证六块 LCD

作为设备所有者，我希望按顺序验证六块 LCD，从而建立完整 key mapping 和恢复证据。

**验收标准：**

- [ ] 使用六张不同编号/颜色图，按 1→6 一次写一块并核验。
- [ ] 六块均显示正确位置、方向和内容，0 错屏、0 邻屏串扰。
- [ ] 任一失败立即取消未执行写入。
- [ ] 失败时按相反顺序恢复已影响屏幕，并记录成功、失败和 unknown。
- [ ] 全部恢复后重跑输入验证，映射不回归。

### M2-08：设计最小 Linux 权限

作为 Linux 用户，我希望只给目标设备和必要接口最小权限，从而避免放开其他设备或键盘。

**验收标准：**

- [ ] G2 与 SDK/profile 激活分开批准。
- [ ] 首次测试优先采用单一节点、当前用户的临时 ACL；任何 ACL 变更仍需明确批准。
- [ ] 持久规则精确匹配 `6602:1000` 和已验证 subsystem/interface。
- [ ] 禁止 vendor-only、`MODE="0666"` 和无证据的 USB/hidraw/input 联合授权。
- [ ] 离线规则 fixture 和安装事务测试不写 `/etc` 或 `/usr`。
- [ ] 真实安装、reload、trigger、插拔和 systemctl 不由自动化执行。
- [ ] 缺权限只给出精确说明，不自动提权。

### M2-09：提供脱敏证据与兼容状态

作为客户、合作方或维护者，我希望看到逐能力的真实验证状态，从而理解产品当前能做什么。

**验收标准：**

- [ ] 每阶段记录 commit、profile 摘要、预期、实际、结果分类、耗时、人工观察和恢复。
- [ ] 公开证据不含 serial、总线位置、`/dev` 编号、用户名、绝对路径、密钥或图片内容。
- [ ] 未知原始帧默认不落盘，只记录长度、类别和计数。
- [ ] 能力状态只能是未验证、已批准待验证、已验证或阻塞。
- [ ] USB ID 命中不能自动产生“型号确认”或“完全支持”声明。

### M2-10：保持 legacy 路径隔离

作为产品负责人，我希望 M2 不让旧服务自动接管目标设备，从而避免把 M3 和系统风险混入
协议验证。

**验收标准：**

- [ ] daemon、probe、debug 和 GUI 不使用目标 active profile。
- [ ] systemd 单元不因 M2 自动安装、enable、start 或 restart。
- [ ] legacy dry-run 不被描述为硬件只读模式。
- [ ] G8 在 M2 之外单独规划，并先解决 close/tcache、自动重启和 shell action 隔离。

## 8. 成功指标

### 8.1 首要指标

| 指标 | 当前 | M2 目标 |
|---|---:|---:|
| 已验证实体输入 | 0 | 6 LCD 键 + 3 圆键 + 3 旋钮全部达到测试次数且 100% 映射正确 |
| 已验证 LCD | 0/6 | 6/6 正确，0 错屏、0 串扰 |

### 8.2 次要指标

- 输入事件本地可见延迟目标 p95 ≤250ms；未达标时报告分布而不是隐藏失败。
- 输入会话连续 10 分钟稳定；各主动写入切片后稳定 60 秒。
- 亮度测试完成可见变化并恢复已知基线。
- 断连后 2 秒内进入 `DISCONNECTED`，重插后自动硬件写入为 0 次。
- helper crash、timeout 和部分响应的自动测试覆盖率为 100% 场景覆盖。

### 8.3 护栏指标

- 未经相应门批准的 SDK/native 加载：0 次。
- 未经批准的 `/dev` open/read/write：0 次。
- 未经批准的 ACL、udev、systemd、sudo 或系统文件修改：0 次。
- 清单外硬件命令和自动重试：0 次。
- G0 CI 对物理硬件的依赖：0。
- 公开证据中的 serial、敏感路径、密钥或图片内容：0。

## 9. 阶段门与退出条件

| 门 | 进入条件 | 退出证据 | 失败结果 |
|---|---|---|---|
| G0 设计/模拟 | 书面规格批准后另批实施计划 | 自动测试、静态安全门、FakeBackend 和 IPC 证据 | 不允许进入 G1 |
| G1 profile/interface | M1 基线一致；单独批准 | 精确 profile 和唯一接口职责 | `BLOCKED` |
| G2 权限 | G1；仅在确需权限时 | 最小权限计划、前后差异、回滚验证 | 不提权；`BLOCKED` |
| G3 输入 | G1；必要时 G2；单独批准 | 输入次数、延迟、10 分钟稳定和断连记录 | 阻塞 G4–G7 |
| G4 初始化 | G3；精确写集合；单独批准 | 实际写集合、结果、恢复和输入回归 | 阻塞 G5–G7 |
| G5 亮度 | G4；已知 B；单独批准 | `B→B-10→B` 三方证据 | 阻塞 G6–G7 |
| G6 单 LCD | G5；已知基线；单独批准 | 单屏位置/方向/串扰/恢复 | 阻塞 G7 |
| G7 六 LCD | G6；单独批准 | 6/6 映射、0 串扰、恢复和输入回归 | M2 保持部分验证 |

批准具有单门、单会话语义，不可向后续阶段继承。G8 legacy/service 激活不属于 M2。

## 10. 错误处理、断连与回滚

- **身份/接口漂移：** 在任何 device access 前拒绝，不选择“最像”的替代接口。
- **权限不足：** 输出稳定错误和最小修复建议，不调用 sudo、不改组、不自动安装规则。
- **read/write timeout：** 达到 deadline 后取消，有限宽限后终止 helper，不无限重试。
- **native crash：** 主进程保持运行，当前阶段失败，状态不晋级。
- **未知事件：** 分类并计数，不触发动作或写屏。
- **写入断连：** 取消剩余队列，受影响输出标记 `unknown`。
- **重插：** 新 session 重新执行 M1 和 G1；不自动恢复亮度、LCD 或 prior approval。
- **恢复未知：** 明确要求机主人工处理，不用 clear、default 或重启伪装成功。

恢复顺序在阶段开始前固定。亮度只恢复已知 `B`；LCD 只恢复已知或机主批准的替代基线。
六屏失败按相反顺序处理已影响屏幕，恢复失败后停止。

## 11. 测试策略

### 11.1 自动化合同测试

- profile 精确匹配、`bcdDevice` 漂移和双接口歧义。
- 状态机全部允许与禁止转换。
- 阶段清单 schema、摘要、commit、操作次数、参数范围和过期行为。
- FakeBackend 的按钮、旋钮、未知帧、断连和抖动。
- helper spawn、timeout、crash、部分输出、无效 JSON 和重复响应。
- 亮度唯一命令、LCD key 边界、顺序、串行化和恢复队列。
- 日志 schema 与 serial/路径/payload/图片内容拒绝规则。
- 主进程 import graph 不包含 `_vendor`，G0 测试不访问 `/dev`。
- udev/安装产物只在临时目录或 `DESTDIR` 检查，不触碰系统状态。

### 11.2 人工真机矩阵

| 测试 | 次数/时长 | 通过标准 |
|---|---:|---|
| LCD 键 1–6 | 每键 10 press/release | 100% 正确、无串键 |
| 圆键 7–9 | 每键 10 press/release | 100% 正确、无误分类 |
| 旋钮 1–3 | 每个左右各 20、按压 10 | 方向和类型 100% 正确 |
| 输入稳定性 | 10 分钟 | 无崩溃、未知事件或未授权写入 |
| 亮度 | 1 个可逆切片 | 可见变化与恢复成功，无 LCD 副作用 |
| 单 LCD | 1 张图 + 恢复 | 唯一目标、正确方向/裁切、无串扰 |
| 六 LCD | 6 张唯一图 + 恢复 | 6/6 正确、0 串扰、恢复有记录 |
| 断连 | 输入阶段至少 1 次 | 2 秒内断连，重插 0 自动写入 |

真机测试不通过故意卡死设备来制造超时；timeout、部分写和 crash 优先用 FakeBackend
与 helper fault injection 验证。

## 12. 权限与安装边界

M2 可以设计、生成和离线测试精确权限模板，但不能因代码合并自动改变系统状态。

最小权限原则：

- 精确 VID+PID；只有证据充分时再限定 interface。
- 只授权已证明必要的 subsystem。
- 桌面会话优先 `TAG+="uaccess"`，禁止 `MODE="0666"`。
- input、hidraw 和 USB 权限分别评审。
- 不把用户加入覆盖所有输入设备的通用组。
- 安装目标是 symlink、未知内容、错误所有者或外部修改时失败关闭。
- udev、service、desktop 分别安装和分别回滚；service 默认不 enable、不 start。

真实 ACL、写 `/etc`/`/usr`、reload、trigger、systemctl、插拔和安装/卸载均为独立人工动作。

## 14. 依赖、假设与风险

### 14.1 依赖

- M1 sysfs-only discovery、设备目录和验证记录。
- Linux 对已确认接口提供可控的只读或读写访问方式。
- 可测试的进程创建、IPC、deadline 和退出状态。
- 机主在未来真机阶段提供人工观察和明确批准。

### 14.2 假设

- 🔶 **假设：** 方案 C 的短生命周期 helper 足以隔离 native crash 和线程泄漏；进程级
  fault injection 必须在真机前验证该假设。
- 🔶 **假设：** 至少一个接口可以在无硬件输出的情况下观察实体输入；若不成立，G3
  必须重新分类为主动协议门并重新评审，不能静默放宽。
- 🔶 **假设：** 亮度与 LCD 写入可以拆成有界单操作；若底层只能组合初始化，能力保持
  阻塞。
- 🔶 **假设：** 首批 Linux 桌面环境支持临时 ACL 或 `uaccess` 的最小权限路径；实际
  属性链必须在目标发行版验证。

### 14.3 主要风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 错误接口或同 ID 复用 | 读取错误输入或写错设备 | 精确 profile、接口人工门、身份漂移失败关闭 |
| native transport 崩溃/卡死 | 主程序退出或设备状态未知 | 隔离 helper、deadline、无自动重试 |
| 隐式 heartbeat/init 写入 | 越过只读阶段 | G3 禁止 SDK；G4 要求完整写集合 |
| 图片协议假设错误 | 错屏、串扰、残留 | 单屏先行、唯一图、逐屏验证和基线恢复 |
| 权限过宽 | 其他用户/设备暴露 | exact ID/interface、`uaccess`、禁止 `0666` |
| 兼容性宣传过度 | 客户信任和支持风险 | 逐能力证据矩阵、Early Preview、禁止外推 |
